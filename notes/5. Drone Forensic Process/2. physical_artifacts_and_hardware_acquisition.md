
# Physical Artifacts & Hardware Acquisition

---

## Scenario — Investigative Starting Point

> A drone is found on the front yard of the President's estate or the PM House lawn.

Before any forensic analysis, ask these questions first to plan the approach:

- **Who owns it?**
- **How did it get there?**
- **Where was it before crashing?**
- **Where was it going?** — Even if it drifted due to wind, what was its programmed destination?
- **What was its purpose?** — Survey, snooping, spying, or something else?

### Internal Inspection — Opening the Casing

![](attachments/Pasted%20image%2020260706190244.png)

Unscrew the four corner screws to remove the top cover. Inside you will find:

- **Flight controller** — mounted at the center (the highest point); has a **serial number** and **QR code** printed on it
- **ESCs** — built-in at the end of each arm (integrated directly onto the board, no separate ESCs)
- **DJI's proprietary PCB design**

**Evidence you can collect:**
- Notes written by the user for themselves
- QR codes
- Linked applications
- **Serial number and model number** — the most important pieces of evidence

> [!NOTE] DJI QR Code Prefix
> If you scan the QR code, you will find that `606` is the standard manufacturer prefix for DJI.

> [!IMPORTANT] Persistence Pays Off
> Nothing comes ready-made in forensics. In 90% of cases, you might start with very few leads, but with persistence, you will eventually solve the case. For instance, numbers printed inside the casing are just numbers — you cannot immediately extract the buyer's identity from them, but they become leads when correlated with other data.

## Linux Systems on the DJI Phantom

Connect the drone via USB to extract files. DJI Phantom systems run Linux internally, exposing multiple network endpoints.

### Network Endpoints & Credentials

| Component | IP Address | Credentials | Notes |
|-----------|-----------|-------------|-------|
| **General CPU** | `192.168.1.1` | `root` / `19881209` | Pictures, videos, telemetry; mounts camera file system; flight controller via `ser2net` |
| **Wi-Fi Extender (GCS)** | `192.168.1.2` | `root` / `19881209` | Runs OpenWRT; connection point for GCS and analysis systems; can be replaced with any OpenWRT system |
| **Camera** | `192.168.1.10` | `root` / `123456` | Camera system access |

> [!TIP] Connection Setup
> Connect the Phantom to an OpenWRT AP, then connect your analysis system to the AP. Instructions available on the project website.

### Data Collection Commands

SSH into the system to gain super-administrator access. From there, navigate memory, create tarballs, and access the root directory:

```bash
# Dump entire memory
ssh 192.168.1.1 -l root "dd if=/dev/mem " | dd of=mem.dd

# Tar the entire filesystem
ssh 192.168.1.1 -l root "tar cf - / " | tar xf -

# Dump the root filesystem partition
ssh 192.168.1.1 -l root "dd if=/dev/mtdblock3 " | dd of=root.dd
```

Additionally, use a modified copy of **Brian Moran's Live Response Collection script** for volatile data.

### Linux Systems — Gotchas (JFFS2 Byte-Swap)

> [!WARNING] Byte-Swapped File System
> The primary file system on the general-purpose CPU is **JFFS2** (Journaling Flash File System v2) on top of an **MTD device**. It is **byte-swapped** on DJI systems, so you cannot mount it directly on an analysis system.

**Steps to handle the byte-swapped file system:**

```bash
# 1. Dump the file system
ssh 192.168.1.1 -l root "dd if=/dev/mtdblock3 " | dd of=root.dd

# 2. Byte-swap it (option A)
dd if=root.dd of=root-swap.dd conv=swab

# 2. Byte-swap it (option B — using mtd-utils)
apt-get install mtd-utils
jffs2dump -b -c -e dest_file.little src_file.big
```

> [!NOTE]
> The JFFS2 file system is mounted on top of another file system on the UAV. To get a complete image, you need to **dump all of the pieces and reconstruct it**.

## SDKs and Live UAV Analysis

> [!IMPORTANT]
> Most flight data resides in **RAM**, and most flight controller software runs off **flash media**. Very little useful data persists after power is removed — only sensor data on removable media survives.

- APIs and SDKs exist for UAVs, similar to many other systems.
- Most commercial UAV applications **will not extract all the data** an analyst needs.
- **Be prepared to develop your own investigative tools** using SDKs when standard forensic tools fail.

### Example — Decoded Telemetry Data

**Battery telemetry:**
```
{designedVolume=5200|fullChargeVolume=5200|currentElectricity=4141|
currentVoltage=11876|currentCurrent=961|remainLifePercent=100|
remainPowerPercent=79|batteryTemperature=20|dischargeCount=2|}
```

| Parameter | Value | Interpretation |
|-----------|-------|----------------|
| Full charge capacity | 5200 mAh | Design spec |
| Remaining charge | 4141 mAh | 79% remaining when received |
| Voltage | 11.876 V | Current battery voltage |
| Current draw | 961 mA | Power consumption at time of capture |
| Battery temp | 20°C | Normal operating temperature |
| Discharge count | 2 | Battery has been through 2 discharge cycles |

> The 79% remaining charge suggests the drone had just taken off and crashed shortly after — nearly 100% of the battery data was recoverable.

**Mission Control (MC) telemetry:**
```
{satelliteCount=6.0|homeLocationLatitude=40.4314293|
homeLocationLongitude=89.31180890000002|
phantomLocationLatitude=40.4314619|
phantomLocationLongitude=-89.31181570000001|
velocityX=0.0|velocityY=0.0|velocityZ=1.0|speed=0.1|
altitude=-8.31500244140625|pitch=0.0|roll=-1.0|yaw=120.0|
remainPower=11878.0|remainFlyTime=0.0|powerLevel=2.0|
isFlying=false|noFlyStatus=0.0|noFlyZoneCenterLatitude=0.0|
noFlyZoneCenterLongitude=0.0|noFlyZoneRadius=0.0|}
```

| Parameter | Value | Interpretation |
|-----------|-------|----------------|
| Satellite count | 6 | GPS was tracking 6 satellites |
| Home location | 40.4314°N, 89.3118°W | Programmed home point |
| Drone location | 40.4315°N, 89.3118°W | Current GPS position |
| Velocity (X/Y/Z) | 0.0 / 0.0 / 1.0 m/s | Hovering with slight vertical movement |
| Altitude | −8.3 m | Relative altitude reading |
| Attitude | Pitch 0°, Roll −1°, Yaw 120° | Orientation at capture |
| Is flying | false | Drone was not in active flight |

> After decoding the raw data bytes, you obtain an immense amount of information — GPS coordinates, velocity, attitude, battery state, satellite lock, and no-fly zone status.

## JTAG Analysis

**In high-level investigations (e.g., CIA labs), forensic experts go as far as using JTAG (Joint Test Action Group) analysis.**

![](attachments/Pasted%20image%2020260706190613.png)

### When JTAG Is Needed

If the drone crashed and caught fire, or if the battery exploded and the system is heavily charred:
- Standard connections are broken
- You must work at the **chip level**
- Open internal circuits and solder fine wires directly onto the chip's connecting pins using specialized **jigs**
- Through JTAG, extract **raw binary data** (1s and 0s) directly from the memory chip

> [!NOTE] Transistor-Level Reading (VLSI)
> At an American experts' meeting, it was demonstrated that even if a chip is not intact, they can read the states of **individual transistors** at the VLSI (Very Large Scale Integration) level to determine which are on or off — reconstructing data from thousands or millions of transistors on a single chip. A specific case from **Afghanistan** required extracting location data from a recovered drone where this method was critical.

### JTAG Limitations

| Limitation | Detail |
|------------|--------|
| **Sealed chips** | Some chips have security seals preventing access |
| **Volatile data** | Certain data does not persist across reboots / power loss |
| **Success not guaranteed** | Further analysis often required |

> [!WARNING]
> JTAG analysis is reserved for **extremely high-profile cases** due to its complexity and the level of expertise required. Success depends heavily on the case priority and chip condition.
